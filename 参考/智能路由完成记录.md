## 一、功能概述

为 Agent 建立智能路由机制：会话模型选择「自动（auto）」时，由本地 RWKV 模型对用户请求做复杂度分类（R0-R3 四级），按配置将请求路由到对应档位的模型/API；分类失败或引擎未就绪时自动回落。

## v3 修订：logits 方案废弃，改为 state-embedding + MLP 头（实测数据驱动）

v2 的「prompt + 数字 token logits」方案经真实模型（rwkv7-g1i-2.9b.int8）40 样本实测**证伪**：
- v1 裸 prompt：30%（预测塌缩到 R0）；v2 User:/Assistant: 包裹：28%（全部塌缩到 R2）
- 根因：2.9B 基座模型不具备指令遵循能力，logits 里无可信分类信号

v3 改用 rwkv-router 论文路径（`paper/scripts/03_classification.py`，test 93.25%）：
```
用户请求原文
  → tokenize（128 token 截断，空文本补 token 0）
  → 零状态 chunked prefill（forward_seq_mean_hidden）
  → 最后一层 FFN 输出 mean pooling → hidden [2560]
  → 标准化 (h-mean)/std → Linear(2560→256) → GELU(tanh近似) → LayerNorm → Linear(256→4) → softmax
  → 4 类概率 → 后处理规则栈（不变）
```

**端到端实测（2.9B int8，含中文增强训练后）**：
| 评测集 | 准确率 |
|---|---|
| golden held-out 314 条（英文为主） | **97.1%**（R0 100%/R1 95%/R2 96%/R3 100%） |
| 手工 40 条（中英混合） | **100%**（R0-R3 全对） |
| 单次分类延迟 | avg 97ms / p95 106ms |

**训练数据陷阱与修复**：golden_balanced.jsonl 的 1783 条中文样本全部是 R0（闲聊），导致首训模型学到「中文→R0」捷径（中文 R1/R2 全塌缩 R0@1.00，英文任务却 96%）。修复：`gen_zh_augment.py` 生成 857 条中文 R1/R2/R3 模板组合样本（仅并入 train，不污染 held-out），重训后中文手工集 45%→100%，英文 held-out 96.2%→97.1% 无回退。

**附带修复的引擎级 bug（影响所有变长 prefill 场景）**：
1. `clear_cache` 清空 CUDA 全部已编译 kernel（T 变化即触发，每次重编译 ~0.5s）——CUDA kernel 地址是启动参数，与缓冲无关，仅需销毁 prefill graph。修复后单次分类 1056ms→~100ms。
2. **SeqBuffers 显存泄漏**：T 变化重建 seq 缓冲时旧缓冲 TensorId 被 Drop，但后端注册表仍持有设备内存（~50MB/次），190 次变长 prefill 即耗尽 22GB 显存。新增 `free_tensor` 后端 API + `SeqBuffers::free`，在 3 处 T 变化点释放。该 bug 同样存在于生产 chat pool（每条不同长度消息泄漏一次）。

### 统一三级模型体系（local / fast / primary ↔ R0-R3）

不再维护「primary/fast」与「R0-R3」两套概念，模型体系与路由档位直接对应：

| 概念 | 语义 | 对应路由档位 | 配置方式 |
|---|---|---|---|
| **local**（rwkv-local） | 本地 RWKV 模型，零成本轻量任务 | R0 + R1 | 固定，无需配置 |
| **fast** | 中档模型 | R2 | 用户可选，未配置回落 primary |
| **primary** | 旗舰模型 | R3 | 用户可选，全局默认回退 |

内部轻量调用（grep/git/web 工具摘要、上下文压缩、会话标题、Explore/FileFinder/Router 等 agent）语义上属于 R0-R1，全部指向 `rwkv-local`。原「fast 强制绑定 rwkv-local」机制已移除（`enforce_fast_model_binding` 删除，替换为 `migrate_fast_model_refs` 一次性迁移：存量 agent/func-agent 的 "fast" 引用改写为 "rwkv-local"，路由 R0/R1 同步改写，`default_models.fast` 若为强制绑定产物则清空）。

### 分类四级定义（对齐 rwkv-router RouteClass）

| Tier | 含义 | 默认模型 |
|---|---|---|
| R0 | 闲聊（问候/致谢/确认） | rwkv-local |
| R1 | 简单任务（单步操作/简单问答/翻译/查询） | rwkv-local |
| R2 | 复杂任务（代码生成/多步推理/多工具协作） | fast |
| R3 | 高难度（调试诊断/错误分析/长上下文/高风险变更） | primary |

### 处理流水线

```
auto 模式请求
  → ① trivial ack 短路（纯规则，零成本）──命中──→ R0
  → ② RWKV 本地分类：tokenize(128截断) → 零状态 prefill → mean-hidden → MLP 头 → 4 类概率
  → ③ 后处理规则栈：safety 升级（R0/R1 且 P(R2)+P(R3)>0.45 → R2）+ sticky tier（短消息不低于上一轮）
  → tier_models 映射 → model_id → 现有 get_client_resolved 链路
  → 任何失败（引擎/head 未加载、超时、维度不匹配）→ fallback（默认 primary）
```

## 二、关键实现决策

1. **分类器 = mean-pooled 最后一层 hidden + 训练 MLP 头**（rwkv-router 论文路径，本地 2.9B 实测 97.1%/100%）。MLP 头权重 `router_head.json`（14MB）部署在 `models/rwkv/`，engine Init 时加载；缺失/损坏/维度不匹配时分类自动禁用并回落 primary（系统无头文件也正常运行）。
2. **分类走推理池专用零状态**：`PoolRequest::Classify { request }` 在 pool 线程同步执行（128 token prefill ~100ms），独立 `classify_state` 每次从零状态快照恢复，与 16 个生成槽位隔离。
3. **分类引擎复用 rwkv-local 已加载模型**：共享常驻显存，无第二次加载。
4. **自动预加载**：desktop 启动序列 `preload_engine_for_router()` 读 `ai.router.enabled`，为 true 时自动初始化引擎。
5. **仅 auto 模式生效**：用户显式选择具体模型时完全不干预。
6. **sticky tier 会话表**：容量上限 1024 超限清空。

### MLP 头训练管线（可复现）

```
1. 数据：client/scripts/router_head/data/golden_balanced.jsonl（16,751 条，源自 rwkv-router）
   + zh_augment.jsonl（857 条中文增强，gen_zh_augment.py 生成）
2. 特征提取：rwkv-rsv/examples/extract_router_features.rs
   （DATA/OUT 环境变量指定输入输出，断点续跑，~10 样本/秒）
3. 训练：cd client/scripts/router_head && uv run train_mlp.py
   --data data/features.jsonl data/zh_features.jsonl
   （AdamW 1e-3 + Cosine 30ep + bs 256 + clip 1.0，dev early stop；
    70/15/15 分层切分，增强集仅入 train；输出 dev/test 准确率 + router_head.json）
4. 部署：copy router_head.json → models/rwkv/router_head.json，重启应用生效
```

## 四、配置说明（app.json `ai.router`）

```json
{
  "ai": {
    "router": {
      "enabled": true,
      "tier_models": { "r0": "rwkv-local", "r1": "rwkv-local", "r2": "fast", "r3": "primary" },
      "fallback": "primary",
      "safety_threshold": 0.45,
      "sticky_enabled": true,
      "timeout_ms": 3000
    }
  }
}
```

tier 值可为已配置模型 id 或逻辑名 "primary"/"fast"/"rwkv-local"。前端入口：设置 → AI 模型 → 智能路由。各 tier 下拉固定提供三个逻辑选项：主力模型、中档模型、RWKV 本地模型（直接走本地推理，无需网络），外加用户已启用的模型列表；rwkv-local 未在用户模型列表中时由后端内置默认配置兜底。

默认模型页（DefaultModelConfig）：primary 下拉 + fast 下拉（现为自由中档槽位，不再绑定 RWKV；未配置回落 primary）。模板页/功能 Agent 选择器（ModelSelectionRadio）新增「RWKV 本地模型」单选项。

## 九、生产化改进轮次（2026-08-21，计划文档 .trae/documents/smart-router-improvements-plan.md）

按五阶段计划完成（自学习闭环经用户决策明确排除：单用户数据偏向性导致过拟合，需专门去偏方案后另行设计）：

### Phase A：P0 逻辑修复
1. **"继续"移出 trivial-ack 词表**（rules.rs）：它是任务推进指令而非确认词，R3 任务中段"继续"被短路到 R0 会导致本地小模型接手复杂任务
2. **trivial-ack 不再写入 sticky 表**（mod.rs）：R3 任务中"ok"→"继续"场景，sticky 参照保持 R3，短消息被正确提回
3. **分类失败不写 sticky 表**：瞬态失败（引擎忙/超时）不再拉低会话档位下限

### Phase B：分类器健康状态 + 测试入口
- `RouterHeadStatus` 全局状态（rwkv_llm.rs，RwLock）：loaded/input_dim/detail（缺失/解析失败/维度不匹配/引擎未初始化）；head 加载提取为 `load_router_head(num_emb)`，加载时即校验维度（原先运行时才发现）
- `route_preview()`（core）：无状态路由预览，不读写 sticky 表
- Tauri 命令：`get_router_status` / `test_router_classification` / `reload_router_head`（config_api.rs + lib.rs 注册）
- 设置页（SmartRouterConfig.tsx + RouterTestPanel.tsx）：三态状态行（绿已加载/黄未加载+原因/灰引擎初始化中，5s 轮询至就绪）+ 测试框（输入任意文本 → R0-R3 概率条 + 路由结论）

### Phase C：路由决策前端可视化
- `ModelRoutingInfo`（events crate）：tier/source/confidence/model_ref/safety/sticky，挂入 `ModelRoundCompleted` 事件（可选字段，向后兼容）
- 管道：`resolve_model_id_for_turn` 返回 `(model_id, Option<ModelRoutingInfo>)` → RoundContext → round_executor → tauri.rs 桥（modelRouting 键）→ EventHandlerModule → ModelRound.routing
- 聊天界面：`RoutingBadge` 组件（ModelRoundItem 首轮顶部渲染 `Auto · R2 · fast · 87%`，悬浮显示完整决策含 safety/sticky 标记）

### Phase D：配置 UX
- tier/fallback 引用已禁用模型时：下拉保留该选项并加"（已禁用）"后缀；引用不存在的模型时显示黄色警告行
- 高级参数折叠区：safety_threshold（0.1-0.9）/ sticky_enabled / timeout_ms（500-10000）

### Phase E：引擎健壮性
- sticky 表 LRU：HashMap + VecDeque 插入序，超 1024 逐个淘汰最旧会话（原为全清）；更新时刷新新鲜度
- head 热重载：`PoolRequest::ReloadRouterHead` pool 消息 + `rwkv_reload_router_head()` + 设置页"重新加载"按钮——router_head.json 更新后无需重启应用

## 十、上下文感知路由：会话摘要方案（2026-08-21，计划 .trae/documents/router-context-summary-plan.md）

**用户定案**：方案 B 模型摘要（每会话维护滚动摘要、控制字数）；取消 128 token 限制（256 = 摘要 128 + 请求 128，恰好 GEMM m_pad 对齐档，延迟不变）；**训练分布必须镜像线上——有摘要是大概率事件（第二轮起必有），故主数据集 71% 为带摘要格式**。

### 运行时管线
- **SessionSummaryService**（`routing/summary.rs` 新增）：LRU 缓存（512 会话）+ in-flight 去重；每轮对话完成后异步 spawn 更新（continuation 风格 prompt 适配无指令遵循的基座模型；低温 0.3、150 token、~2.7s）；后处理剥回声/双换行截断/词数预算 120；失败保留旧摘要（首条失败→无摘要，均为已训练分布）
- **分类输入格式**：`Summary: {摘要}\nRequest: {请求}`（有摘要）/ 裸请求（无摘要）；`build_classify_input` 保证训练/线上严格一致
- **CLASSIFY_MAX_TOKENS 128→256**：双段预算；超长输入防御（防秒级 prefill/超时/OOM），复杂度判断无需全文
- route/route_preview 增加 `summary` 参数；设置页测试入口传 None（裸分类）
