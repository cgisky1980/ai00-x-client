# 邀请码机制 — 实施方案设计 v2（写入 参考/邀请码机制-实施方案设计.md）

双轨制：**普通用户邀请轨（C 端裂变）+ 专业推广员轨（渠道计酬）**，共用一套归因与结算底座。

## 一、普通用户邀请轨（承接 v1，摘要）

- 名额：tier 基础（free=1/basic=2/pro=4/flagship=6）+ 消费解锁（¥50/+1，上限+10）+ 有效激活回补，封顶 20
- 奖励：一代首充 10%（封顶 500）+ 留存奖 200 + 二代 30% 折算 + 新人礼双边 +10%；月度 5000 积分上限
- 有效邀请 = 首笔充值；风控：IP/设备聚集、频率、黑名单 → T+1 审核

## 二、专业推广员轨（新增）

**定位**：KOL/社群主/渠道代理，平台直签，**平级单层、不发展下线**（无推广员招募推广员的组线机制——这是与用户轨"二级赠金"的本质区别，避免团队计酬）。

**准入**：申请（联系方式+渠道说明+粉丝规模）→ 后台人工审核 → 签《推广合作协议》→ 开通推广员身份。

**计酬**：
- 专属**渠道码**（每推广员可发多个，支持分渠道投放统计），归因优先级高于个人码：注册时 `channel_code` 与 `invite_by` 互斥归因
- 阶梯佣金：按其渠道月度充值流水阶梯，默认 15% / 20% / 25% 三档（阈值可配）
- **月结 T+7**：生成月度结算单 → 人工复核 → 发放
- 结算载体：MVP 走积分/赠金入账 + 人工提现工单（后台线下打款留痕）；**预留 `settlement_type`（credit/cash）字段与提现申请 API**，未来接灵活用工/劳务报酬合规通道时切换，客户端无需改动
- 推广员奖励**不计入**普通用户 5000/月上限，比例与结算周期独立配置

**服务器端**：`promoter`（身份表：审核状态/协议签署）、`channel_code`（码表：归属推广员/备注名/启用状态）、`channel_attribution`（注册归因：channel_code or invite_by 互斥）、`channel_settlement`（月度结算单：流水/佣金比例/状态/凭证）；端点：`POST /me/promoters/apply`、`GET /me/promoters/channel-codes`、`GET /me/promoters/settlements`、admin 侧审核/报表/结算单生成。注册 hook 归因逻辑与首充/留存奖励 hook 完全复用用户轨。

**前端**：MVP 仅预留——推广员报表与结算走 Salvo admin 后台（web 端）；web-ui 侧暂不做推广员中心，只在数据层（inviteApi/credits ledger）兼容 `channel` 来源标记，M3 视运营情况再决定是否在客户端内嵌推广员中心。

## 三、前端与宣传（同 v1）

- 邀请中心：CreditsScene 第三页签（朱砂 CTA 一处、墨阶 token、衬线标题、`invite` 命名空间）
- 新用户侧：Login 副文案 + 注册成功新人礼卡片
- 宣传位：充值成功态 / 签到 toast / AccountConfig 常驻入口 / UpgradeDialog 次级按钮 / 官网申请成功态 / 二期 canvas 邀请卡图
- 埋点：k 系数、邀请→首充转化、渠道分报表

## 四、分期（v2 调整）

- M1 MVP（约 2 周）：用户轨全量（规则+名额+首充奖+新人礼+T+1 结算+邀请中心页签+宣传位①②③④）；推广员轨**只落数据模型与归因字段**（channel_code 表 + 注册互斥归因 + admin 手工配置推广员）
- M2：留存奖/二代奖自动结算、邀请卡图、官网宣传位、推广员申请入口 + 渠道分报表 + 月度结算单生成
- M3：审核后台完善、提现通道对接（settlement_type 切换）、风控与增长看板

4. 推广员佣金阶梯数值与协议模板（需运营/法务给出）
